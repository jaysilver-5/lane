# FirstLane QA audit — 2026-10-07

## Verdict

**Not release-ready.** The underlying access rules are substantially correct: guest access is limited to 10 fixed questions, verified free access to 40 fixed questions, premium deep links are denied, and paid access unlocks the 500-question bank plus rehearsals and offline content. However, the free-tier experience has three user-facing discrepancies, one of which can strand an in-progress free session. The production release gate also correctly remains blocked because live services, store acceptance, legal review, native accessibility, and approved content are not configured or signed off.

## Scope and evidence

- Reviewed the Expo/React Native client, access rules, billing client, access cache, protected content delivery, RevenueCat webhook, and Supabase migrations.
- Ran `npm run check`: TypeScript passed; all 70 tests passed; source and content checks passed.
- Ran `npm run web:export`: passed and produced a web export.
- Ran a browser smoke pass across 29 routes: all rendered after accounting for normal asynchronous startup.
- Exercised guest, verified-free, paid-demo, sign-out, sign-in restore, premium deep-link, 40-question rehearsal, and offline-pack states.
- Ran `npm audit --omit=dev --audit-level=high`: 26 advisories (15 high, 11 moderate).
- Ran `npm run release:check`: correctly failed with missing production configuration, unapproved content, and incomplete acceptance records.
- `expo-doctor` could not complete its Expo API schema check because the TLS connection failed. This is an environment/network limitation, not a confirmed project defect.

Screenshots were captured and inspected in the selected in-app browser during this run. The browser surface did not expose a local-file save path for those captures, so the durable artifact is this report and the screenshots remain in the audit trace.

## Confirmed strengths

1. **Access boundaries are fail-closed.** Unverified users resolve to guest access; invalid, future, expired, revoked, or malformed grants do not unlock paid content.
2. **Guest and free samples are fixed.** Guest receives exactly 10 IDs; verified free receives exactly 40 IDs, split 20 road signs / 20 road rules. Repeated free sessions do not rotate premium questions into the pool.
3. **Deep links are protected.** A guest opening a premium question ID sees an Ontario Complete gate; a paid user sees the full question and explanation.
4. **Premium features are gated.** The 40-question rehearsal, offline pack, and full topic access require paid access. The paid demo produced a 40-question rehearsal and loaded the 500-question bank.
5. **Paid state is account-scoped.** Signing out immediately removed premium access; signing back into the purchasing demo account restored it.
6. **Fulfillment is server-authoritative.** Client purchase success alone does not unlock access. The checkout waits for `firstlane_my_access`, protected content requires a verified grant and approved release, and downloads are size/hash validated.
7. **Duplicate-payment defenses exist.** Pending purchase state is persisted before the store sheet opens, requests are account-pinned, and duplicate taps/account switches are guarded.
8. **Release safety is explicit.** Production remains blocked until approved content, real service configuration, store checks, legal review, native accessibility, deletion, refund/restore, and backend security acceptance are complete.

## Findings

### P1 — Free/guest topic counts overstate what the user can actually practise

The topic catalog and topic detail use full-bank counts and objectives for every tier. In the live pass, a guest was shown **20 questions** for “Basic shapes and sign families,” but the resulting session was **1 of 1**. A verified free account was shown the same 20-question claim but received **1 of 4**. Another guest topic advertised **24 questions** and then opened a paywall because that topic had no guest sample.

Impact: the free-tier promise is internally inconsistent and makes a fixed sample pool look like full topic access. Users cannot tell which topics or counts are actually included before starting.

Evidence: `app/topic.tsx` derives the displayed count/objectives from the full loaded topic pool, while `src/state/AppState.tsx` filters the actual session through `allowedQuestions(...)`.

Recommendation: compute and display `availableCount` for the current access tier. Lock topics with zero available questions before navigation, and label counts such as “4 free samples · 20 in Complete.”

### P1 — Generic paywall action can strand a normal free session

Reproduction:

1. As a guest, start a 10-question quick session.
2. Navigate to Practice rehearsal and press Start.
3. In the access sheet, choose **Save Complete session & use Free**.
4. Return to Today: the primary action is **Start a quick session**, not **Continue practice**.

The action always calls `parkPremiumSession()`, which moves `state.active` into `pausedPremium` even when the active session is a valid free/guest session. That parked session is only resumed through the paid-access branch, so a free user cannot get back to it.

Evidence: `app/_layout.tsx` uses the action unconditionally; `src/state/AppState.tsx` implements `parkPremiumSession` without checking whether the active session contains premium content.

Recommendation: show this action only when the active session is actually premium-incompatible, or make `parkPremiumSession` a guarded no-op for free-compatible sessions. Add a regression test covering a free active session followed by a gated premium action.

### P1 — Web signup consent is broken for pointer and standard checkbox-key activation

The terms control is exposed as a checkbox, but it has no `aria-checked` attribute in the rendered DOM. Mouse/coordinate clicks did not change its state, and Space did not activate it. The form remained blocked with “Accept the terms and privacy notice to continue.” Pressing Enter while focused did toggle it and allowed signup.

Impact: mouse/touch web users and keyboard users following standard checkbox behavior cannot create a free account. This also blocks the main guest-to-free conversion path.

Evidence: `app/auth/sign-up.tsx` uses a React Native `Pressable` with `accessibilityRole="checkbox"` and local state, but the web rendering did not expose or update checked state.

Recommendation: use a native web checkbox path or a shared checkbox component that renders `aria-checked`, supports click/tap, Space, and Enter, and has a visible focus state. Add browser tests for all activation methods.

### P1 — Dependency audit reports unresolved high-severity advisories

`npm audit --omit=dev --audit-level=high` reported **15 high** and **11 moderate** advisories, including `braces` and `node-forge`. The audit's automatic fixes require breaking version changes and even propose incompatible Expo downgrades, so `npm audit fix --force` is not safe.

Impact: release risk is not yet understood. Some findings may be build-time-only or unreachable in the shipped app, but they require package-owner triage rather than acceptance by default.

Recommendation: map each advisory to runtime/build exposure, upgrade Expo/Metro/Router through supported release lines, and record accepted exceptions with evidence.

### P2 — Refund reversal is not handled by the entitlement mirror

The commerce RPC only applies `NON_RENEWING_PURCHASE` and `CANCELLATION`. A `REFUND_REVERSED` event is stored as ignored/manual review. The refund tombstone also remains, so replaying the original transaction cannot automatically restore the grant.

Impact: an affected App Store customer can remain incorrectly downgraded to free after a refund reversal until manual intervention.

RevenueCat documents `REFUND_REVERSED` as an App Store webhook event: <https://www.revenuecat.com/docs/integrations/webhooks/event-types-and-fields>.

Recommendation: define and test an explicit refund-reversal path that clears the matching tombstone/refund state and safely restores the original transaction grant.

### P2 — Guest plan labeling is misleading

The plans page labels **FirstLane Free** as **Your plan** for any non-paid user, including guests. The same card describes 40 post-signup samples, while the current guest actually has 10.

Evidence: `app/plans.tsx` uses `!access.full ? 'Your plan' : 'Always available'` instead of distinguishing `guest` from `free`.

Recommendation: show “Available after free signup” for guests and reserve “Your plan” for verified free accounts.

### P2 — Checkout and results emit web runtime errors

The browser pass recorded repeated `Unexpected text node: . A text node cannot be a child of a <View>.` errors during checkout/payment transitions and two `Invalid DOM property transform-origin` errors on results. The results screen also showed a development error toast, and the “PRACTICE ACCURACY” caption visually crowded the score ring.

Impact: the paths still completed, but the error volume can obscure real defects and indicates non-clean web rendering.

Recommendation: isolate the stray text child in the checkout/payment transition, update the SVG rotation/origin implementation for web, and add a clean-console browser assertion for checkout and results.

### P3 — Web deprecation warnings are noisy

The pass repeatedly logged deprecated `pointerEvents` and `shadow*` style warnings, plus the expected Expo Notifications web warning. These are not current blockers but should be removed before using console cleanliness as a release signal.

## Flow health

1. **Onboarding and guest entry — Healthy.** Clear guest path, correct 10-sample banner, no payment required.
2. **Guest quick practice — Healthy.** Starts a 10-question mixed session and prevents premium question access.
3. **Topic discovery and topic practice — Needs work.** Full-pack counts/objectives are shown to guest/free users; actual sessions are shorter or gated.
4. **Free account creation — Failing on web pointer/Space input.** Enter-key workaround exists but is not acceptable.
5. **Free-tier enforcement — Healthy at the data layer.** 40 fixed questions; no premium rotation or premium deep-link access.
6. **Upgrade and paid demo — Healthy with console errors.** Paid demo unlocked 500 questions, a 40-question rehearsal, direct premium questions, and offline pack state.
7. **Sign-out/sign-in entitlement isolation — Healthy.** Paid access closed on sign-out and restored for the purchasing account.
8. **Refund/reversal lifecycle — Partially covered.** Refund revocation is tested; refund reversal and live store delivery are not.
9. **Route integrity — Healthy.** All 29 audited routes rendered; empty/error states were present where IDs or completed sessions were absent.
10. **Production release readiness — Blocked as intended.** Required configuration, approval, native/store, backend, legal, and content checks remain incomplete.

## Verification gaps

- No real iOS or Android store sheet, RevenueCat webhook delivery, sandbox refund/restore, or signed native build was available.
- Supabase migrations and `supabase/tests/commerce_acceptance.sql` were reviewed but not executed against a live database.
- Native SecureStore/SQLite behavior, notification permission flow, haptics, native keyboard behavior, and account deletion were not exercised.
- The in-app browser viewport override did not apply, so the visual pass used the default browser viewport with the app's 560px content layout rather than a verified 390px device viewport.
- This is not a WCAG compliance certification; accessibility evidence is limited to visible behavior and the browser accessibility tree.

## Recommended release order

1. Fix the session-parking bug and add its regression test.
2. Fix web signup checkbox semantics and pointer/keyboard behavior.
3. Make guest/free topic availability and counts truthful before entry.
4. Add `REFUND_REVERSED` handling and acceptance coverage.
5. Clear checkout/results runtime errors and triage dependency advisories.
6. Complete the existing production release checklist with real services, approved content, native builds, store sandboxes, and named sign-off.
